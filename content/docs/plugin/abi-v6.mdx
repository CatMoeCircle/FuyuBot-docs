---
title: ABI v5 → v6 迁移
description: 服务调用现在经过宿主，提供方能识别调用方；插件重编一次即可
---

从 0.1.4 起，插件之间的服务调用由宿主转交。最直接的变化：像 `/help` 这样的服务
终于能可靠地知道**是哪個插件**在做登记——包括调用方在自己的线程上发起的情况。

## 你要做什么

绝大多数插件只需要**重新编译一次**：

```bash
cargo build --release
```

- 用 `define_plugin!` 的 Rust 插件：`cargo build` 就够了，版本号由 `fuyubot-abi` 提供。
- 手写 C / C++：换用新的 `fuyubot_plugin.h`（`#define ABI_VERSION 6`）。
- Go（c-shared）：重新 `go build`。这类库一旦加载就不能卸载，换版本后要重启进程。
- `plugin.json` 里的 `"abi": 6` 只是给人看的建议值，写不写都不会影响加载。

> 0.1.4 宿主不会加载 0.1.3 编译的插件（反过来也一样）。看到
> `plugin_init 返回了失败句柄` 就是这件事：重编插件即可。

## 调用方：写法不变

```rust
host.call_service(
    "fuyubot.help.commands",
    "register",
    r#"{"name":"mycmd","description":"我的命令"}"#,
)?;
```

不需要传插件名，也传不了别人的名字——身份由宿主判定。

## 提供方：能准确拿到调用方

```rust
// 服务方法里
let caller = host.current_plugin();   // Some("fuyubot.manage") / None（宿主自己调）
```

| 调用发生在哪 | 拿到的调用方 |
| --- | --- |
| 插件 `start()` / 事件回调 / 中间件 | 该插件（与 0.1.3 相同） |
| 插件自己起的线程（tokio task、`thread::spawn`） | **该插件**（0.1.3 会拿不到） |
| A 调 B 的服务、B 再调 C 的服务 | C 看到的是 **B**（0.1.3 看到 A） |
| 宿主自己调（`plugin list` 等） | `None` |

`None` 表示「不是某个插件在调」，不要拿它当错误。

## 返回值：`NULL` 与空串

服务方法返回的字符串，约定收紧了一点：

| 提供方返回 | 调用方看到 |
| --- | --- |
| `NULL` | **失败**（服务不存在 / 没有该方法 / 入参非法），具体原因在宿主日志里 |
| 空串 `""` | 成功，但没有输出 |
| 其他字符串 | 成功，内容就是返回的 JSON |

所以以前用 `NULL` 表示「成功但无内容」的服务，改成返回 `""`。
字符串仍然是**提供方持有、读完即弃**：调用方要保留就当场拷走（`HostApi::call_service` 已经替你拷好了）。

## C / Go 调用方

建议改走同一个入口：

```c
const char *reply = host->call_service(host->host_ctx, "fuyubot.help.commands",
                                       "register", "{\"name\":\"mycmd\"}");
if (reply == NULL) { /* 失败 */ }
```

自己 `get_service` 拿到表再直接调函数指针仍然能跑，但那次调用绕过了宿主，
提供方只会拿到 `None`——拿不到调用方。

## 排错

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 启动时插件全被跳过，日志有 `plugin_init 返回了失败句柄` | 插件还是 0.1.3 编的 | 重编插件 |
| 服务的归属字段是空的 | 有一条调用路径绕过了宿主（自己取表直调） | 改用 `host.call_service` |
| 服务调用从「成功、无内容」变成了失败 | 提供方返回了 `NULL` | 提供方改成返回 `""` |

## 一个仍然存在的限制

在服务方法里调用 `set_config` 时，配置会写到**调用方**的段，而不是提供服务那一方的段。
这是 0.1.3 就有的行为，0.1.4 没有改。需要写自己的配置，请在 `start()` 或自己的回调里做。
