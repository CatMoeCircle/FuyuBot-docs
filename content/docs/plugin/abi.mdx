这是**唯一**的跨语言契约：形状只有 `fuyubot-abi/src/lib.rs` 一份实现，C 头文件
`fuyubot_plugin.h` 由 cbindgen 从它生成（**产物，不是源码**，别手改）。宿主侧所有桥在
`fuyubot-loader/src/runtime.rs`。**改 ABI = 改那个文件 + 加版本号。**

## 插件必须导出的符号

v3 的四个契约符号仍是必需/可选的底线；v4 另外导出三个**静态符号**，让
宿主与静态工具**不 dlopen** 也能看见插件是按哪个 ABI 编的（版本值仍只能运行时判定）。

| 符号 | 类型 | 必须吗 | 说明 |
| --- | --- | --- | --- |
| `plugin_init` | `unsafe extern "C" fn(*const HostApiVTable) -> PluginHandle` | **必须** | 校验 VTable、构造状态；返回失败句柄（`abi_version == 0`）= 拒绝加载 |
| `plugin_start` | `unsafe extern "C" fn(PluginHandle, *const c_char) -> i32` | 可选 | 拿到配置 JSON，注册订阅 / 工具 / 中间件；返回 `0` 成功 |
| `plugin_stop` | `unsafe extern "C" fn(PluginHandle)` | 可选 | 卸载前调一次，回收自己的状态 |
| `plugin_free_string` | `unsafe extern "C" fn(*mut c_char)` | **必须** | 释放**插件自己**分配的字符串（宿主从不 free 插件的指针） |
| `plugin_free_handle` | `unsafe extern "C" fn(PluginHandle)` | v4 可选 | 版本不匹配、不能调 `plugin_stop` 时，用来释放 `plugin_init` 分配的状态 |
| `fuyubot_abi_version` | `unsafe extern "C" fn() -> u32` | v4 可选 | 返回编译期 `ABI_VERSION`；静态工具只检查“存在”，值要运行时看 |
| `plugin_manifest` | `unsafe extern "C" fn() -> *const c_char` | v4 可选 | 自描述 JSON（名字 / 版本 / `inject` / `soft_inject`）。宿主在 `plugin_init` **之前**读；名字与 `init` 不一致只告警，依赖以 manifest 为准 |

符号名由常量钉住（`SYM_PLUGIN_INIT` / `SYM_PLUGIN_START` / `SYM_PLUGIN_STOP` /
`SYM_PLUGIN_FREE_STRING` / `SYM_PLUGIN_FREE_HANDLE` / `SYM_PLUGIN_ABI_VERSION` /
`SYM_PLUGIN_MANIFEST`），`PluginLoader::load_with_config` 按这些名字 `lib.get(...)`。
C++ 里必须把它们放进 `extern "C"` 块，否则名字被 mangle，宿主 dlsym 不到。

`PluginHandle` = `{ abi_version: u32, size: u32, context: *mut c_void, name: *const c_char }`；
`is_valid()` 的判据是「`abi_version != 0` **且** `context` 非空」，所以插件的 `context` 不能是
`NULL`。`PluginHandle::FAILED` 是全零版本号，`const _` 里有
`assert!(PluginHandle::FAILED.abi_version == 0)`。

三点值得记住：`plugin_manifest` 在 `plugin_init` **之前**读（宿主得先知道你的依赖才能排顺序）；
版本不匹配时**只能**用 `plugin_free_handle` 收尾，那一刻 `plugin_stop` 不会被调；
卸载顺序是 `plugin_stop` → 回滚注册 → 最后才 drop 那个 `Library`。

## HostApiVTable：`host_ctx` + 27 个函数指针

`version` 在偏移 0、`size` 在 4、`host_ctx` 在 8，其余 **27 个是函数指针**，全是 `Option<...>`；
总大小 = `2 * size_of::<u32>() + 28 * size_of::<*const c_void>()`（`host_ctx` + 27 个函数），
由 `const _` 里的 `offset_of!` / `size_of` 断言钉死。每个函数第一个参数都是 `host: *mut c_void`。

下表签名省略第一个参数 `host`：

| # | 字段 | 签名 | 宿主实现 | 说明 |
| --- | --- | --- | --- | --- |
| — | `version` | `u32` | `ABI_VERSION` | 必须等于 `ABI_VERSION`；首个字段，插件能在读其它任何字段之前先比一次 |
| — | `size` | `u32` | `size_of::<HostApiVTable>()` | 老宿主 + 新插件时先比 `size` 再读尾部字段，读越界就是 UB |
| — | `host_ctx` | `*mut c_void` | `&HostRuntime` | 每个函数都原样回传；插件作者看不见它（`HostApi` 自动带上） |
| 1 | `on` | `(update_type, filter_json, callback, user_data) -> SubscriptionHandle` | `api_on` | 订阅；`filter_json` 里的 `event_type` 选通道，其余键做负载匹配；`NULL` / 空串 / `"null"` = 收全部 |
| 2 | `off` | `(handle) -> ()` | `api_off` | 退订；句柄 drop 时宿主也会整批回滚 |

| 12 | `td_invoke_simplified` | `(method_name, params_json) -> RequestId` | `api_td_invoke_simplified` | 给参数补上 `@type = method_name`；参数不是对象就整份替换成 `{"@type": …}` |
| 13 | `td_execute` | `(request_json) -> *const c_char` | `api_td_execute` | **同步**执行不碰网络的方法（`td_json_client_execute`），当场返回响应 JSON。**不发请求号、不进请求留档、不等响应通道**——所以能在事件回调里用；宿主没接 TDLib 时返回 `NULL` |

## 服务作用域

每个插件加载时拿到**自己的一层 `Context`**，于是：

- `provide_service` 注册的服务只对本插件（和它更深的子作用域）可见——**默认私有**。
  两个插件注册同名服务**不冲突**，各用各的实现。
- 宿主注册在根上的公共服务（事件总线 / 服务容器 / 工具表 / 中间件管线）沿父链照样看得到。
- 真要跨插件共享才用 `provide_service_shared`：它写进程级的根表，同名会和别人撞
  （直接报 `ServiceNameExists`）。
- 插件卸载时，它那层作用域连同里面的服务一起消失。

跨插件联动的端到端示例（`/help` 的命令注册表）见[插件联动](./linkage.mdx)。

两条形状上的硬要求：

- **第一个参数总是 `host: *mut c_void`**：裸函数指针没有捕获环境，VTable 里放不了闭包；
  不给显式上下文就只能靠进程级全局，那样一个进程只能有一个宿主、测试也没法并行。
- **每个函数指针字段都是 `Option<...>`**：C 侧传 `NULL` 合法，非 `Option` 字段收到 `NULL` 就是 UB。
  Rust 侧 `HostApi::from_raw` 一次解包校验全部 27 个，之后调用路径上没有 `Option`、也没有 panic 分支。

### 服务的形状：`ServiceVTable`

一个服务就是一张 C 结构表——宿主和插件都不需要知道服务的 Rust 类型，按名字调方法即可：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `name` | `*const c_char` | 服务名，NUL 结尾 UTF-8 |
| `version` | `u32` | 提供方填的协议版本（协商用，宿主不校验） |
| `size` | `u32` | `size_of::<ServiceVTable>()` |
| `context` | `*mut c_void` | 提供方的实例数据，**原样传给每个方法** |
| `methods` | `*const ServiceMethod` | 指向 `method_count` 个连续的方法项 |
| `method_count` | `usize` | 方法项个数 |

每个方法项是 `{ name: *const c_char, func: ServiceMethodFn }`，
`ServiceMethodFn = fn(context: *mut c_void, input_json: *const c_char) -> *const c_char`。

### 怎么调方法

**v6 起这次调用经过宿主**（VTable 第 24 项 `call_service`），Rust 侧写法没变：
`HostApi::call_service(name, method, input_json)`。

- 宿主替你把这个调用转给提供方，并在调用期间记下调用方是谁；
- 被调方因此能在方法里问出**真实调用方**（下一节），插件在自己的线程上调进来也成立；
- 返回 `NULL` = **失败**（服务不存在 / 没这个方法 / 入参含 NUL）；
- 返回**空串** = 成功但没有输出（对方方法返回了 `NULL`）；
- 其余 = **提供方持有的** NUL 字符串，立刻拷走——它只在本次调用返回后、
  下一次宿主函数调用之前有效（与 `list_tools` / `get_config` 同一套线程局部缓冲）。

失败时別只说「调用失败」：第 25 项 `last_error` 带着原因（哪个服务、哪个方法、为什么）。
`HostApi::call_service` 已经自动把它拼进错误里，Rust 侧直接 `?` 就能看到：

```text
服务调用失败：fuyubot.help.commands.register: 没有名为 fuyubot.help.commands 的 service
```

> `NULL` 与空串的分工是 v6 才明确的（v5 时两者都当「成功但没有输出」）。
> 提供方想说「成功、无返回值」请 `return ""`，不要 `return NULL`。

### 怎么找到服务：`list_services`

不想硬编码别人的服务名，就先问一句：

```rust
let catalog = host.list_services();   // JSON 数组文本
// [{"name":"fuyubot.help.commands","version":1,
//   "methods":["register","list"],"plugin":"fuyubot.help"}, …]
```

`plugin` 为 `null` 的是宿主预置服务（`fuyubot.host.scope` / `.plugins` / `.identity`）。
清单从**调用方**的作用域链算，所以自己的私有服务也在里面；只给元数据，不给 vtable 指针。

C / Go 侧**同样走这一步**：`host->call_service(host_ctx, name, method, input_json)`。
自己 `get_service` 拿表再直调仍然能跑，但宿主不在场，被调方就拿不到调用方。
脚本插件（Python / JS）目前 **没有**服务调用接口——薄 SDK 只覆盖订阅 / 请求 / 日志 /
工具元数据，见[脚本插件](../script/index.mdx)。

### 调用者身份：`current_plugin`

服务方在方法里问一句「谁在调我」：

```rust
let caller = host.current_plugin();   // Option<String>
if let Some(name) = caller {
    // {"ok":true,"plugin":"fuyubot.manage"}
}
```

取值规则（v6）：**正在被别人调用时就是调用方**；其余时候是宿主最后把控制权交给的那个插件
（在插件自己起的线程上则是 `NULL`）。身份由宿主判定，插件自报不了，也拿不到别人的。
`/help` 的命令归属就是这么来的。

v5 只有第二级，所以「插件在自己起的线程上调服务」时归属会静默变成 `null`；
这条差异以及 v5 → v6 的完整清单见 [ABI v5 → v6 迁移](./abi-v6)。

### 宿主预置的服务

宿主在根上预置了三个服务，任何插件沿父链都看得见，直接 `call_service` 就行：

| 服务名 | 方法 | 协议 |
| --- | --- | --- |
| `fuyubot.host.plugins` | `report` | 无参 → `{"plugins":[{name, state, …}]}`，进程内插件快照；`state` ∈ `active` / `pending` / `failed` / `activating`，`pending` 带 `missing`、`failed` 带 `reason` |
| `fuyubot.host.identity` | `usernames` | 无参 → `["FuyuBot"]`，自身全部活跃用户名（`usernames.active_usernames`）；没登录 / 没接 TDLib 时是 `[]` |
| | `me` | 无参 → `getMe` 的原始 `user` JSON；没登录时 `null` |
| `fuyubot.host.scope` | `scope_create` | `{}` → `{"handle":N}`，开一个子作用域 |
| | `scope_enter` | `{"handle":N}`；成功 `null`，失败 `{"error":"…"}` |
| | `scope_leave` | 忽略入参；离开当前作用域 |
| | `scope_drop` | `{"handle":N}`；成功 `null`，失败 `{"error":"…"}` |

`fuyubot.host.plugins` 与 ABI 第 8 项 `list_plugins` 同源，只是多一条走服务这条路
（内置 `/plugins` 插件就是这么读「进程里真在跑的」插件清单的）。`fuyubot.host.identity`
是「我是谁」：宿主登录成功拿到 `getMe` 之后写进去，之后**每条 `updateUser`（id 是自己那条）
都会刷新它**，所以改名字 / 改用户名之后读到的就是新值。`fuyubot-simplify` 的 `on_command`
靠它把「点名给别人的命令」挡在插件外面——纯内存读取，不是 TDLib 请求，
**在命令回调里调它不会卡接收循环**。面板与 `fuyubot status` 显示的账户行也来自同一份数据
（经 `.fuyubot/status` 跨进程过去）。
`fuyubot.host.scope` 是中间插件批量托管脚本时开子作用域用的，见[架构](../dev/architecture.mdx)。

句柄类型（`SubscriptionHandle` / `ToolHandle` / `ServiceHandle` / `MiddlewareHandle` / `RequestId`）
都是 `#[repr(C)]` + 单个 `u64`（断言钉住 `size_of == size_of::<u64>()`）；
`LogLevel` = 1..5（`Error` / `Warn` / `Info` / `Debug` / `Trace`），`Stage` = 0..5；
`WaitHandle` = `{ id: u64, matched: u32, _reserved: u32, payload_json: *const c_char }`。

## 内存所有权：三条硬规矩

1. **谁分配谁释放**。插件通过 `plugin_init` 返回的 `name`、以及插件自己分配的任何字符串，
   都由插件持有；宿主**绝不** free 它们。插件要给宿主一个需要接管的临时字符串，只能走
   `plugin_free_string` 那套约定。
2. **宿主返回的字符串是线程局部缓冲**。`list_tools`、`get_config`、`WaitHandle::payload_json`
   指向宿主的一块复用缓冲（`thread_local! HOST_STRING`），**只在下一次调用宿主函数之前有效**。
   要留着就当场拷走，并且**不要试图释放它**——VTable 里没有 host 侧的 free 函数，这是设计不是遗漏。
3. **`ServiceMethodFn` 的返回值由提供方持有**，调用方读完即弃。

## 版本协商

| 位置 | 谁比 | 不匹配的后果 |
| --- | --- | --- |
| `ABI_VERSION`（当前 `6`） | 编译期常量，两侧共同引用 | — |
| `HostApiVTable::version` | 插件侧 `HostApi::from_raw` | `AbiError::VersionMismatch` |
| `HostApiVTable::size` | 同上 | `AbiError::VTableTooSmall` |
| 某个函数指针是 `NULL` | 同上 | `AbiError::MissingFunction("<字段名>")` |
| `PluginHandle::abi_version` | 宿主侧 `PluginLoader` | `AbiMismatch`：**拒绝加载** |

版本不兼容时宿主**不能**调 `plugin_stop`——那是对一个不认识的 ABI 下手。v4 起插件可以
导出 `plugin_free_handle`，让宿主在版本不匹配时释放 `plugin_init` 分配的状态；老插件没有
这个符号，那部分内存仍然回收不了。字段只增不改，新增一律追加在尾部。

**版本 2 的改动**：尾部追加了 `td_execute`（同步执行，见上表第 13 项）。

**版本 3 的改动**：尾部追加了 `get_config` / `set_config`（第 18 / 19 项），让插件能读全局配置、
写自己的段。

**版本 4 的改动**：
- `register_tool` 增加 `handler` / `user_data`，工具终于能真的执行；
- 尾部追加 `call_tool_result`（同步拿工具结果）与 `list_plugins`（插件报告）；
- 尾部追加 `provide_service_shared`（第 20 项）：服务默认按插件作用域隔离，要共享得显式走它；
- 新增静态导出 `plugin_free_handle` / `fuyubot_abi_version` / `plugin_manifest`。

**版本 5 的改动**：尾部追加 `simplify_invoke` / `simplify_invoke_result`（第 21 / 22 项），
把 `fuyubot-simplify` 的语义下沉到宿主——**所有语言**的插件都能用「发消息等结局 / 超时撤回 /
bot 与用户号挑不同反应方法 / Markdown → entities / 富消息本地块树」，不再只有 Rust 有。
详见[「simplify 操作表」](#simplify-操作表)。

**v5 的尾部追加**：`current_plugin`（第 23 项）。服务方法终于能问出「现在是谁在调我」，
拿到宿主判定的**权威**插件名——`/help` 的命令归属不再需要入参自报。当时是**纯追加、不改语义**，
靠 `size` 协商，所以没跳版本号。

**版本 6 的改动**：尾部追加 `call_service`（第 24 项），**服务调用改成经过宿主**。
宿主因此在调用期间知道调用方是谁，`current_plugin` 拿到的就是它——于是
「插件在自己起的线程上调服务」也认得出调用方，嵌套调用报的是直接调用者而不是最初的调用方。
同时 `call_service` 的返回值约定收紧：`NULL` = 失败，**空串** = 成功但无输出。

同一次 v6 里还追加了三项（25 / 26 / 27）：`last_error`（失败原因）、`list_services`
（服务发现）、`set_config_section`（跨插件写配置）。这三项是**纯尾部追加**，靠 `size`
协商、不再跳版本号——老宿主（没有这三项）会明确拒绝新插件，而不是读到错位的指针。

另外 `set_config` 的判定对象从「调用者」改成了「执行者」：服务方法里写配置现在落
**提供方**自己的段（以前会错写进调用方那段），`get_config` 不受影响。

> ⚠️ 这次**跳了版本号**（`5` → `6`）：字段是纯追加，但 `current_plugin` 的**取值来源变了**，
> 属于静默的行为差异，不能只靠 `size` 协商。v5 插件在 v6 宿主上、v6 插件在 v5 宿主上
> 都会 `AbiMismatch`（拒绝加载），**重编一次即可**（仓库里所有插件与模板都从 `ABI_VERSION` 取值）。
> 完整清单见 [ABI v5 → v6 迁移](./abi-v6)。

追加字段本身不破坏老插件（它们先比 `size`），但按契约「改 ABI 就加版本号」，
v4 / v5 / v6 各跳过一次——**用旧版本编出来的插件会被宿主拒绝加载**，重新编一次即可。

## simplify 操作表

`simplify_invoke` / `simplify_invoke_result` 收的是一张**操作表**而不是「一个方法一个函数指针」：

```json
{"op": "send_message", "args": {"chat_id": 123, "input_message_content": {…}}}
```

**为什么不是每个操作一个函数指针**：那样以后每加一个方法都要升一次 ABI 版本、三个仓库一起动。
一张表之后，**加操作不动 ABI**。

### 结果怎么回来

`simplify_invoke` 返回 `RequestId`，结果走**既有的** `"response"` 通道回到发起插件——
JS/TS 的 `invokeAsync`、Python 的 `invoke_async`、Go 的 channel、Rust 的 `ResponseRouter`
全都原样接住，没有新的回投机制。负载长这样（成功失败同形状，只看 `ok`）：

```json
{"@type":"simplifyResult","op":"send_message","ok":true,"result":{…},"request_id":123}
{"@type":"simplifyResult","op":"send_message","ok":false,"error":{"code":"timeout","message":"…"}}
```

`error.code` 是稳定的英文代号，可以拿它分支：`timeout` / `send_failed` / `tdlib` /
`missing_field` / `bad_args` / `unknown_op` / `async_op` / `host` / `missing_op`
（`op` JSON 缺字符串字段 `op`）/ `simplify`（`SimplifyError` 里没单独归类的兜底）。

### 入参的形状

`args` 基本就是对应 TDLib 方法的参数（键名以 `td_api.tl` 为准），**认不出的键原样透传**
（宿主照 schema 只警告不拦，TDLib 升版加了新参数也不用等 ABI）。外加两个统一项：

- `timeout_ms`（默认 30 000）：整次操作共用的等待预算；
- 文本字段（`text` / `caption`）可以是字符串（按纯文本），也可以是
  `{"text":"…","parse_mode":"markdown|markdown_v2|html"}`——宿主替你走 `parseTextEntities`
  换成 `formattedText`。已经是 `formattedText` 就原样放过。

### 操作清单

同步（不碰网络，`simplify_invoke_result` 也能跑，回调里安全）：

| op | args | 返回 |
| --- | --- | --- |
| `parse_text_entities` | `text` / `parse_mode` | `formattedText` |
| `rich_from_markdown` | `markdown` / `is_rtl` / `detect_automatic_blocks` | `inputMessageRichText`（可直接塞进 `send_message` 的 `input_message_content`） |
| `list_ops` | — | `{"sync":[…],"async":[…]}` |

异步（要等 TDLib 应答，只能走 `simplify_invoke`）：

| op | 语义 |
| --- | --- |
| `send_message` | 发 → 等响应拿临时消息 → 等**发送结局**；超时先 `deleteMessages(revoke)` 撤回 |
| `send_message_album` | 整组一个预算，逐项等结局，任一项失败即返回 |
| `edit_message_text` / `edit_message_caption` / `edit_message_media` / `edit_message_reply_markup` | 等响应（`edit_message_reply_markup` 不给 `reply_markup` = 移除键盘） |
| `delete_messages` | `chat_id` / `message_ids` / `revoke` |
| `answer_callback_query` | 点了内联按钮必须回，否则客户端一直转圈 |
| `forward_messages` | `message_ids` 排序去重、最多 100 条；只等响应 |
| `react` / `unreact` | **自动挑方法**：bot 只能 `setMessageReactions`，用户号用 `add/removeMessageReaction` |
| `add_reaction` / `set_reactions` | 显式走某一条路（省一次 `getMe`） |
| `me` / `my_id` / `is_bot` | 身份 |
| `chat_member` / `is_chat_admin` / `am_i_chat_admin` | 管理权（`right` 是 `chatAdministratorRights` 的字段名，如 `can_delete_messages`） |
| `download_file` | 等到 `updateFile` 报下载完成，返回最终的 `file` |
| `invoke` | 逃生舱：`args.request` 是**完整**的 TDLib 请求 JSON，发 + 等响应 |

操作表可以问出来：`{"op":"list_ops"}`。

## 为什么本 ABI 一个可变参数函数指针都没有

Rust 的 `extern "C" fn(.., ...)` 确实稳定（能写、cbindgen 也能生成），但**本 ABI 一个都没用**，
理由只有一条：`...` 会把**参数类型和个数校验全部丢掉**。VTable 里 27 个函数的参数都是固定的，
用 `...` 只会让 C 侧传错参数从编译错误降级成运行期 UB。

将来真要加，正确的声明形状是（C 侧）：

```c
typedef void (*FuyubotLogFn)(uint32_t level, const char *format, ...);
// Rust 侧对应：unsafe extern "C" fn(level: u32, format: *const c_char, ...)
```

两条必须知道的事：

- 变参部分**不能**是唯一的参数——C 要求 `...` 之前至少有一个具名参数。
- **变参函数指针跨不了 ABI 的 `Option` 优化**：`Option<fn(..., ...)>` 不是 niche 优化，占**两个指针宽**，
  必须显式判空。本 crate 里那条
  `size_of::<Option<unsafe extern "C" fn()>>() == size_of::<*const c_void>()` 断言只对**非变参**函数指针
  成立；普通函数指针字段能享受 niche 优化（`NULL` 就是 `None`），这也是「整个 VTable 所有字段都能是
  `Option<...>` 且不撑大布局」的前提之一。

## 五种语言各自声明的兼容 ABI 版本

| 语言 | 声明在哪 | 值 | 怎么生效 |
| --- | --- | --- | --- |
| C | 头文件 `fuyubot_plugin.h` 里的 `#define ABI_VERSION 6` | 6 | 模板里写 `if (host == NULL \|\| host->version != ABI_VERSION) return failed;` |
| C++ | 同一份 `fuyubot_plugin.h` | 6 | 同上（导出符号放 `extern "C"`） |
| Rust | `fuyubot_abi::ABI_VERSION` | 6 | `define_plugin!` 把它填进 `PluginHandle::abi_version`，并导出一份 `fuyubot_abi_version` |
| Python | **脚本不接触 ABI** | — | 由 `fuyubot.script` 承载（标准 ABI 的 cdylib，v6，尾部带 `current_plugin` + `call_service`），`abi_version` 它填 |
| JS / TS | **脚本不接触 ABI** | — | 同上，同一个 `fuyubot.script` 插件 |

脚本插件走的是薄 SDK（PyPI / npm 的 `fuyubot`）→ 原生桥 → `fuyubot.script` 这条路，
**作者永远不碰 C ABI**；ABI 版本由承载它的那份 cdylib 声明。那是一个**独立仓库的插件**，
不属于运行时本体，见[脚本插件](../script/index.mdx)。

## 回调为什么是 `C-unwind`

`EventCallbackFn` 与 `MiddlewareCallbackFn` 都是 `unsafe extern "C-unwind" fn(...)`。
`extern "C"` 边界上逃出去的 panic 会直接 **abort 整个进程**，宿主来不及 `catch_unwind`；
`C-unwind` 允许 unwind 穿过边界，宿主就能接住、记一条日志、继续跑下一条更新。
对 C/C++ 而言两者 ABI 完全一致；C++ 异常同样会穿过这个边界，**请自己在回调内处理完**。

`define_plugin!` 生成的三个导出函数还会把插件代码包在 `catch_unwind` 里——两层都要。

<Callout type="warn">
  版本不兼容时宿主**不会**调 `plugin_stop`：那是对一个不认识的 ABI 下手。字段只增不改，
  新增一律追加在尾部；改动必须同时抬 `ABI_VERSION`。
</Callout>

宿主 ABI 版本是 `fuyubot_abi::ABI_VERSION`（当前 **6**）；插件编译时用它做校验，不用手抄。
