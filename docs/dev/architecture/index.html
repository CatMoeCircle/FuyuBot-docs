架构与数据流

一个宿主进程 + N 个动态库插件，以及它们之间的三段数据流

结论先说：一个宿主进程 + N 个动态库插件（cdylib）。插件不认识 Rust，只认识 HostApiVTable； 宿主是唯一实现这张表的 crate（fuyubot-loader）。脚本插件（Python / JS / TS）不改变这个结构 ——目录形态由两个中间插件（fuyubot_python_host / fuyubot_js_host）托管，旧的胶水形态 则把解释器子进程藏在自己的 cdylib 里。

本文只讲结构与数据流；构建、发布与排错见 开发文档。

crate 依赖方向

箭头指向「依赖的那一边」（A --> B = A 依赖 B）：

边允许吗
fuyubot-core → fuyubot-tdlib禁止
fuyubot-abi → fuyubot-core禁止
event / service / tool / middleware 互相依赖禁止（彼此不依赖）
fuyubot-tdlib-sys → 任何 fuyu crate禁止（它是最底层）
fuyubot-loader → 四个机制 + tdlib + abi + core允许（只有它）

组合只发生在两处：HostRuntime::new（把四个机制 install 进 Context）与 HostRuntime 里的 20 个 unsafe extern "C" 桥（VTable 的 20 个函数指针各对应一个）。四个机制 crate 绝不彼此调用。

启动顺序：先 attach TDLib，再 load 插件

不起接收循环——关键顺序点4loader.load_with_config(dll, config)逐个 dlopen 插件、跑 plugin_start；插件在这里就开始发请求5pipeline.spawn_dispatch()拿到 ReceiveLoop，开始把更新分发给插件

为什么不能反过来：attach_tdlib 之前 td_send 走「没接 TDLib」分支（请求只留档 + 合成请求号， 起点 1 << 48），而插件在 plugin_start 里就发请求（模板与示例都这样）；分发排在插件加载之后， 否则插件漏订阅。--replay / --no-tdlib 故意不 attach——回放是离线验证。

主链路

process（吃 &str）只是 process_value 的前半段（解析 JSON 再交给它）；接收循环那条路 本来就有 Value，所以走 process_value。

阶段数值谁跑它
Stage::PreUpdate / PreRoute / InPlugin / PostResponse0 / 1 / 2 / 3UpdatePipeline::process_value
Stage::PreToolCall / PostToolCall4 / 5目前没有生产调用方（只有 fuyubot-middleware 自己的测试）

六阶段的数值在 fuyubot-abi::Stage，与 fuyubot-middleware::Stage 一一对应，由 runtime.rs 的 stage_numbers_match_the_middleware_crate 测试钉住。

三条容易搞错的语义：

  • 归属是「额外定向」，不是「排除广播」：emit 发给所有订阅者，emit_scoped(owner, …) 是 「全局 + 该归属」。响应因此对所有插件透明。
  • 中间件一条更新跑一遍，不是每个监听器跑一遍：InPlugin 的产出就是所有监听器看到的版本 （按监听器各跑一遍的话，第 N 个会看到被改过 N 次的 payload）。
  • 过滤器里的 event_type 键只用来选通道，不参与负载匹配；等响应写 {"event_type":"response","request_id":N}。

注册作用域与卸载

HostRuntime::plugin_scope() 给这次加载分配一个 owner id，之后所有跨 ABI 的注册 （订阅 / 工具 / 服务 / 中间件）都记在这个 owner 名下（RegistrationKind + Registration）。 scope.commit() 保留；提前 drop（init 失败、start 报错、ABI 不匹配）或 LoadedPlugin 被 drop 时， rollback_owner(owner) 一次性撤掉这批注册；宿主自己（owner 0）不受影响。

LoadedPlugin 的字段声明顺序就是卸载顺序：先 plugin_stop，再 rollback_owner， 最后 _lib: Library 才 drop——到这一步动态库才真正卸载。

中间插件要批量托管脚本时，用内置 scope 服务（get_service("fuyubot.host.scope")）开子作用域： create 出的子作用域从当前作用域栈继承 owner（脱离加载线程的场景——比如 watch 线程——要先建 root scope 再 enter，否则 owner 退化成宿主 0，卸载时回滚不到），注册落在子作用域里， rollback_scope 可以只撤这一批；插件卸载时连 owner 一起收。

唯一的例外是 Go 的 c-shared 库：它的运行时有线程与信号处理器，卸载后进程会 access violation （0xC0000005，而且崩在退出那一刻）。PluginLoader 用文件里的 Go buildinfo 魔数认出 Go 产物， 对这类库 plugin_stop 与注册回滚照跑，但故意不卸载那个 Library，让它映射到进程退出。 代价是「同一进程内反复加载同一个 Go 插件」不可靠（热重载路径），收益是 Go 插件能正常用。

依赖与激活顺序

每个插件有两个依赖列表：inject（硬）与 soft_inject（软）。它们只影响准入与顺序， 不影响加载——插件已经 dlopen 进来了，只是还没轮到它跑。

四条规则：

  • 硬依赖不齐 → 不激活，停在 Pending。这是「等」，不是「错」——提供者可能只是排在后面还没轮到。
  • 软依赖不齐 → 照样激活，只是排在有软依赖的后面（两轮扫描：先扫软的也齐了的，再扫其余）。
  • 每轮只推进一个 fiber，先退后进。一轮的推进量有保险丝（2n + 16），万一依赖图构了环也不会卡死。
  • 激活失败 → 级联：依赖它的插件一并标 Failed，因为那个提供者永远回不来了。

Pending 与 Failed 的分界就是「还可能好」和「不会好了」：is_permanently_missing 只在 提供者已经 Failed 时返回真。服务表里没有、也没有同名 fiber 的依赖，一律保持 Pending—— 它可能是以后才出现的服务（比如另一个插件在外层作用域里 later 才 provide）。

四大机制与内核

crate里面有什么
fuyubot-corelib.rs 的 Kernel（Created → Started → Stopped）；context.rs 的 Context（Arc<RwLock<HashMap<TypeId, Arc<dyn Any + Send + Sync>>>>）；effect.rs 的 Effect（Box<dyn FnOnce()> 回滚守卫，#[must_use]，merge() 后注册者先撤销）；plugin.rs 的 Plugin trait + define_plugin!；manager.rs 的 PluginManager（load / load_all / unload / reload + DFS 三色拓扑排序）
fuyubot-eventEventBus / Filter / SubscriptionHandle / EventContextExt
fuyubot-serviceServiceContainer / ServiceHandle / ServiceContextExt
fuyubot-toolToolDescriptor / ToolRegistry / ToolHandle / ffi 模块 / ToolContextExt
fuyubot-middlewareStage / Middleware / Next / Pipeline / MiddlewareHandle / MiddlewareContextExt

三条共用约定：

  • 回调错误类型由 core 定：四个 crate 不能互相依赖，所以 fuyubot_core::Result<T> 是全仓唯一允许 boxed error 的地方。
  • 与 Context 的集成 = install(ctx) + 扩展 trait：返回的 Effect 要一直持有，否则服务立刻从 Context 消失。
  • 所有注册都返回句柄且 #[must_use]：四个 Handle 内部都包着 core::Effect，drop 即回滚。

各自的一条要点：

机制要点
事件emit 在锁外面调回调，所以回调里再 on / emit / off 不会自锁；某个回调返回 Err 会中断本次广播并把错误抛出去。Filter 用点分路径（"message.chat.id"）做字段相等匹配
服务命名容器（跨语言插件报不出 Rust 的 TypeId）。同名重复注册报错；get::<T> 类型不匹配返回 None，用 contains + type_of 区分「没注册」和「类型不对」
工具call_tool = 查表 → 权限门 → input_schema → 处理器 → output_schema。handler: Option<ToolHandlerFn>，None 表示「只有元数据的声明型工具」；注册/注销用 on_change 广播（不认识事件系统，要不要转成事件总线由宿主层决定）
中间件洋葱模型，next.run(ctx) 前是进入段、后是退出段。run(stage, ctx) 会先复制层列表再执行，所以中间件里再 use_middleware 不会自锁；不调 next.run 就是不往下走

内核的几条语义：

  • Context 只有 &self：provide 返回 Effect，drop 即注销，所以调用方必须持有它。
  • Effect::merge 是 LIFO：a.merge(b) 的撤销顺序是 b → a。
  • 加载顺序由依赖决定，卸载是加载顺序的倒序；load_all 报错会把本次已加载的卸掉，不留半加载。
  • 有依赖者时 unload 拒绝（HasDependents），不级联。
  • reload 之所以能工作，是因为管理器存的是 Arc<dyn Plugin> 而不是 Box。

绑定层与运行时（fuyubot-tdlib-sys / fuyubot-tdlib）

两个 crate 一人一半：-sys 只出类型、不做加载，tdlib 才是运行时。

cratebuild.rs 做什么src/ 里有什么
fuyubot-tdlib-sys
绑定层		拿 td_api.tl + 生成编译期两份产物（无条件执行，没有 feature 早退）build_support.rs（与另一个 crate 共用的缓存/下载设施）、ffi.rs（函数指针 + 符号名 + 指针形状 const assert）、tl_schema.rs（解析与 JSON 互转）、tl_codegen.rs + docs.rs、schema.rs、td_api.rs（include! 生成物）
fuyubot-tdlib
运行时		只管 vendored 动态库 + 把库 staging 到可执行文件旁边loader.rs / loader/vendored.rs / client.rs / authorize.rs

三条边界约定：

  • 重导出的路径不变：fuyubot_tdlib:: 根上重导出 -sys 的 ffi / schema / td_api / tl_schema 与 TdApiSchema / EntryKind / TlEntry / TlParam / SchemaError / TdApi / DEFAULT_LOG_VERBOSITY，所以既有调用方一行都不用改。
  • 两份源码被两边共用：build_support.rs 与 loader/vendored.rs 各自的 build.rs 都用 #[path] 引同一份，因此它们只能依赖 std 与可选依赖。
  • 两份 metadata 必须一致：[package.metadata.fuyubot] 在两个 crate 里各有一份，值要对得上 （守卫测试 metadata_is_in_sync_between_the_two_crates）。

loader::resolve 按这个顺序找动态库：

  1. TDLIB_TDJSON_PATH（文件或目录）
  2. vendored 目录
  3. 可执行文件所在目录（ExeDir）
  4. Linux 带版本号的系统库
  5. 裸库名（真去 dlopen 试一次）

全失败返回 TdlibLoadError::NotFound，消息里逐条列出 [1]…[4] 的尝试与原因。

真正加载必须走 loader::open_library（Windows 绝对路径会走 LOAD_WITH_ALTERED_SEARCH_PATH）， 不要直接用 Library::new——以后任何新增的加载动态库的地方都走它。

@extra 是字符串（RequestId::to_extra()）；route() 遇到非数字的 @extra 会退化成更新，不 panic。

td_api.tl 转成了什么（只在编译期）

两份产物来自同一个解析结果，而且 tl_schema.rs 被 build.rs 用 #[path] 引同一份实现，所以「编译期 写出来的形状」与「运行时读回去的形状」不可能漂移。生成规则：类 → 带 #[serde(tag = "@type")] 的 enum； 函数 → 带 METHOD / RESULT 常量的 struct（派生 Default，没填的字段不写进请求）；类字段一律 Option<Box<T>>（断互递归 + 对上「缺字段就是没有」）；认不出的类型降级成 serde_json::Value；Rust 关键字转义（r#type）；文档四级齐全（类 / 变体 / 函数 / 字段）。归类只认 ---functions--- / ---types--- 分区标记，认不出来时构建直接失败。 check_request 那套元数据仍然保留——它做的是生成类型做不到的本地校验（生成类型只能保证结构对， 挡不住「用错方法名」）。
