发布

两套发布资产（TDLib 库 / fuyubot 本体）与文档站的静态部署

仓库有两套互不替代的发布资产，tag 前缀不同，别混：

资产tag生产方谁消费
TDLib 动态库 TDLib-<os>-<arch>TDLib-v<版本>build-tdlib.yml + .github/scripts/*.sh构建期（fuyubot-tdlib 的 loader 表）
fuyubot 本体 fuyubot-<os>-<arch>.zipv<版本>release-bot.yml终端用户下载、解压即跑

TDLib 资产（构建期契约）

消费方是 crates/fuyubot-tdlib/src/loader/vendored.rs 的 ASSETS 表，生产方是 .github/workflows/build-tdlib.yml 的 matrix；tests/release_assets.rs 会读 workflow 双向比对， 漂了就红。四条硬要求：

  1. tag 必须精确是 TDLib-v<版本>（下载 URL 由 release_url() 拼）；
  2. 资产名精确等于 ASSETS 表的值，不带扩展名，<os>-<arch> 用 cargo 口径（x86_64 / aarch64）；
  3. 内容必须是 .tar.gz（.zip 会被 extract_library 当裸库原样写出，得到坏文件还不报错）；
  4. 加平台只动 ASSETS 表 + CI matrix，两边同时加（macos/x86_64 故意不在表里：没有那个 runner）。

fuyubot 本体（用户下载即用）

运行时仓库的 release-bot.yml 在 v* tag（或手动 dispatch）上按平台编 fuyubot-cli + 三个内置插件， 分两份单独打包：本体（可执行文件 + 该平台的 tdjson，从 TDLib-v<版本> 那个 Release 取）与 内置插件（plugins/）。publish 把它们叠成各平台一个 zip 再挂 Release：

fuyubot-sdk-<os>-<arch>.zip 由 SDK 仓库（FuyuBot-SDK 的 release-sdk.yml）发布， 不混进运行时的包。

平台集合与 ASSETS 表一致：Windows / Linux 各 x86_64 + aarch64，macOS 只有 aarch64。

中间产物（fuyubot-*.tar.gz / fuyubot-plugins-*.tar.gz / fuyubot-sdk-*.tar.gz）只留在 Actions artifacts 里，不挂 Release——它们是构建产物，不是发布形态。

三条契约：资产名与 ASSETS 同口径、zip 里保留顶层目录 <资产名>/、 tdjson 与可执行文件同级（靠 loader 优先级 2「可执行文件所在目录」命中）。 zip 只在 publish（Linux runner）里生成，Windows runner 的 bash 没有 zip 命令。

GitHub Actions 在本机验不了。改 workflow 的组包步骤时，把 Package 与 Merge 两段 bash 原样抠出来在本机跑一次， 解压产物验证 --version / init / run --replay / --no-login --background 全通—— 这一步是踩过「改了却没验」之后定的规矩。

文档站

website/ 是静态导出（output: 'export'），产物 out/：

把 out/ 交给任意静态托管即可；GitHub Pages 记得 public/.nojekyll（_next/ 以 _ 开头会被 Jekyll 吞掉）， 正式域名在构建前设 NEXT_PUBLIC_SITE_URL（绝对 URL 是烘进产物的）。

发布前过一遍提交检查清单：文档站与仓库里的工程台账都更新、cargo build/test/fmt 三条绿、 没把凭据写进任何文件。
