工具与中间件

注册工具元数据、call_tool、六阶段洋葱管线

工具（tool）是「有名字、有 schema、可被别的插件或宿主调用」的能力；中间件（middleware） 是流经更新管线时的洋葱式拦截点。两者的注册都记在当前插件的作用域下： 插件卸载（或加载失败）时宿主一次性回滚这批注册。

注册工具：只登记元数据

本版 ABI 只登记元数据：register_tool 收的是一份 JSON 描述，里面没有函数指针的位置， 登记出来的工具一律是 handler: None 的声明型工具。插件无法让宿主回调进自己来执行工具。

字段类型说明
namestring全局唯一，建议 插件名.工具名
versionstringsemver，默认 0.1.0
descriptionstring给人看的一句话
input_schemaJSON Schema描述入参
output_schemaJSON Schemanull / {} 表示不校验
required_permissionsstring[]调用前要过的权限门
idempotentbool默认 false
timeout_msnumber默认 30000
is_asyncbool默认 false
callablebool读出时才有：本进程里有没有可调处理器

handle 无效（id == 0）表示登记被拒（重名、schema 不合法等）。

本版 ABI 登记的工具没有处理器，所以对这类工具调 call_tool 只会拿到无效请求号 （id == 0）——声明型工具的用途是「让它出现在 list_tools 里、被别人发现」，不是被真的执行。

list_tools() 返回全部工具的元数据 JSON 数组。宿主线程局部缓冲：读完即弃， 要留就当场拷走，不要试图释放它。

脚本侧的名字不同：Python 是 host.register_tool(...)，JS 是 host.registerTool(...)， 都只收 name / description / input_schema。

中间件：六阶段洋葱

阶段数值谁跑它
PreUpdate0收到更新、还没解析
PreRoute1已解析 @type，路由前
InPlugin2分发给监听器之前；一条更新只跑一遍
PostResponse3响应发出之后
PreToolCall4工具调用之前（目前没有生产调用方）
PostToolCall5工具调用之后（同上）

数值就是 ABI 里的 stage 参数，与 fuyubot-middleware::Stage 一一对应。

要点：

  • 回调是 C-unwind 的 fn(user_data, stage: u32, payload_json) -> i32：返回 0 继续、非 0 中断本阶段。 中断只影响本阶段剩下的层，管线继续走下一阶段（已经改过的负载照样往下传），宿主记一条 warning。
  • 中间件一条更新跑一遍，不是每个监听器跑一遍：InPlugin 的产出就是所有监听器看到的版本。 按监听器各跑一遍的话，第 N 个会看到被改过 N 次的负载。
  • 洋葱模型：进入段在「继续往下」之前，退出段在之后。不往下走就是中断。
  • Rust 侧注册返回的 MiddlewareHandle 也是 #[must_use]，drop 即摘除。
  • 阶段号非法或回调为空会让 use_middleware 直接返回无效句柄（不会静默挂个空层）。

想看订阅与双通道怎么配合，见 订阅与事件；工具调用的格式最终由宿主层决定， 契约本身见 ABI 契约。
