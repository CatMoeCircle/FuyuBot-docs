调用 TDLib

td_invoke、请求号与 response 通道、便捷封装

插件不直接碰 tdjson 库，只把请求交给宿主：

VTable 函数输入用途
td_invoke完整请求 JSON（含 @type）手写整份请求
td_invoke_simplified方法名 + 参数 JSON宿主把参数补上 @type = 方法名（参数不是对象就整份换成 {"@type": …}）
td_execute完整请求 JSON，同步返回响应只给「不碰服务器」的方法用（parseTextEntities / getTextEntities 之类）。当场有结果、不发请求号

前两个返回请求号（RequestId），不是结果。结果从响应通道回来。

请求号与 response 通道

  • 响应负载是 TDLib 原始 JSON，宿主额外挂一个数值型 request_id（来自它注入的字符串 @extra， 别自己设这个字段）。
  • 要等某条响应：过滤器写 {"event_type":"response","request_id":5}。event_type 键只选通道， 不参与负载匹配（见 订阅与事件）。
  • 没接 TDLib 时（--replay / --no-tdlib）请求只留档并返回合成请求号（从 1 << 48 起）， 链路照样能测通，但永远不会真的到达 TDLib。

wait_for_update 阻塞当前线程，timeout_ms == 0 表示只检查当前状态； 返回的 payload_json 是宿主线程局部缓冲，只在下一次宿主调用前有效——要留就当场拷走。

方法名以 TDLib 为准

⚠️ TDLib 的方法名 ≠ Telegram Bot API 的方法名。TDLib 里所有发送都是 sendMessage， 内容类型靠 input_message_content 区分；sendPhoto / sendDocument / sendLocation （HTTP Bot API）在 TDLib 里不存在。

你在 Bot API 里习惯的在 TDLib 里这么写
sendPhoto / sendDocument / sendLocationsendMessage + input_message_content.@type = inputMessagePhoto / inputMessageDocument / inputMessageLocation
message_thread_idtopic_id（{"@type":"messageTopicThread","message_thread_id":N}）
reply_to_message_idreply_to（{"@type":"inputMessageReplyToMessage","message_id":N}）
顶层 disable_notification / protect_contentoptions（@type: messageSendOptions）里
顶层 caption在内容类型里（inputMessageText / inputMessagePhoto …）
parse_mode没有这个字段；formattedText 只有 text + entities（要标记先走 parseTextEntities）
file_id（updateFile）在 file.id，不是顶层

便捷封装：fuyubot-simplify

Simplify 只简化输入，不改变输出：每个方法都经 td_invoke* 发出，原始更新照旧对插件可见。 参数形状是一个方法一个结构体 + 短字段名，调用方不用拼 TDLib 的嵌套 JSON； 文本格式（Markdown / HTML）不自己解析，经同步的 td_execute 问 TDLib 的 parseTextEntities。

它的完整 API 参考（按功能范围分组）在 Simplify 封装； 想知道为什么这么拼、为什么这么等，看开发 › simplify 封装是怎么实现的。 本页只留跟「请求号 + 线程」有关的那两件事——它们是这层最容易被搞错的部分。

等到什么才返回

每个方法都等到结果才返回，不交回请求号。分两类：

类别等到什么返回值
发送类（send_message / send_message_album / 富消息）响应（还没发出去的临时消息）+ 它的发送结局：updateMessageSendSucceeded（里面有最终 Message）或 updateMessageSendFailed最终 Message（相册是与 medias 同序的 Vec）
其余（edit_* / delete_message / answer_callback_query）只有响应改完的 Message / ()
  • 两步之间按临时消息的 old_message_id 精确对号，同一会话里别人的结局不会串进来；
  • 相册的 timeout_ms 是整组共用的一个预算（先等 Messages 响应、再等 N 条结局），不是每项各等一次；
  • 超时先撤回：到期还没结局，就先 deleteMessages(revoke = true) 把那条没发出去的消息撤掉，再返回 Timeout——发出去的撤不回，没发出去的会被取消；
  • @type == "error" 的响应一律变成 SimplifyError::Tdlib（例如 Message is not modified）， 封装层不重试：限流该等多久是调用方的事。

回调里用 *_then

等更新要靠接收循环那个线程送回来，而插件的更新回调就跑在它上面——在那里等待=自己卡自己， 等到的一定是超时。每个等待版都有一个 *_then：把等待挪到另一个线程，结局交给闭包。

它们返回那个线程的 JoinHandle——插件要在 stop() 里 join 掉，否则动态库卸载之后线程还在跑库里的代码 （未定义行为）。三个内置插件就是这么写的，可以照抄。

最小上手

方法名与参数名由 every_request_simplify_builds_passes_the_real_schema 拿真 td_api.tl 烤出来的元数据 （TdApiSchema::compiled()）逐条校验，离线就能跑。

两条时间线

  1. 便捷方法把等待收进去了：发送类等响应 + 发送结局，其余等响应 （"response" 通道，事件类型 RESPONSE_EVENT，只发给发起请求的那个插件）。 想自己接原始 JSON，底层出口 wait_response / wait_for_update 仍然公开。
  2. WaitHandle::payload_json / td_execute 的返回串都是宿主临时的线程局部缓冲， 只在下一次宿主调用之前有效。要拿数据就立刻读，或者用 *_json / wait_response（它们已经替你拷好了）。

HostRuntime::td_send 在没接 TDLib 时只留档 + 发合成请求号（从 1 << 48 起），td_execute 在同样 情况下返回 None——所以本文的每个方法在离线状态下都能被跑通、但不会真的到达 TDLib（Markdown 会退回纯文本）。
