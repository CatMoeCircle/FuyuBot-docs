插件总览

一个 cdylib 就是一个插件，四种导出符号

一个插件 = 一个 cdylib（.dll / .so / .dylib）。宿主 dlopen 它，只认四个导出符号， 其余全部能力都经 HostApiVTable 回调宿主。插件不认识 Rust 内核，也不需要认识。

符号必须吗干什么
plugin_init必须校验 VTable、构造插件状态；返回失败句柄（abi_version == 0）= 拒绝加载
plugin_start可选拿到配置 JSON，注册订阅 / 工具 / 中间件
plugin_stop可选卸载前调一次，回收自己的状态
plugin_free_string必须释放插件自己分配的字符串（宿主从不 free 插件的指针）

契约细节（字段布局、内存所有权、版本协商）见 ABI 契约。

两种形态

原生插件脚本插件
语言Rust / C / C++Python / JS / TS，外加一层 Rust 胶水 cdylib
边界与宿主同进程，C ABI 函数调用一个插件一个解释器子进程，一行一个 JSON
崩溃拖垮宿主只有子进程死，宿主记一条错
起步fuyubot-sdk init demo --lang rustfuyubot-sdk init demo --lang python / js

脚本插件的 cdylib 里只有一行 script_plugin!，逻辑全在脚本里——它不改变「一个 cdylib 一个插件」这个结构。

最小闭环

  • fuyubot init 重复执行会被挡住（不覆盖你改过的配置）；三个键都有默认值，最简可以只有 [bot]。
  • 插件名只允许字母、数字和 . _ -（会拼进源码与 TOML）；目录名里的 . / - 换成 _ 当 crate 名 （fuyubot.weather → fuyubot_weather）。
  • 产物落在哪：plugin install <工程目录> 只看 <工程>/target/{release,debug} 与工程目录本身。 插件若是当前 workspace 的成员，cargo build -p <crate> 默认把产物放在仓库根的 target/，于是它找不到 ——加 --target-dir <工程目录>/target，或直接指着产物装（脚本插件必须用前者，否则脚本不会被拷）。
  • SDK 走源码开发时设 FUYUBOT_SDK_PATH 指向 FuyuBot-SDK 仓库的 crates/，生成的插件会写 path = "…"； 不设就写 crates.io 版本号。

fuyubot 管运行，fuyubot-sdk 管开发，两个都不编译插件：编译是作者自己语言工具链的事 （cargo build / cl /LD / gcc -shared）。fuyubot plugin install 只复制已编好的产物。

写插件要知道的六件事

事说明
回调是 extern "C-unwind"用 extern "C" 的话，逃出去的 panic 直接 abort 整个进程，宿主来不及 catch_unwind
一个 crate 只展开一次 define_plugin!四个符号名是 ABI 定死的，展开两次就是重复定义
ABI 版本目前是 2不匹配时宿主拒绝加载，而且不能调 plugin_stop 收状态
订阅句柄必须活着Rust 侧是 #[must_use] 的守卫，drop 就是退订
插件 emit 不是广播只送自己 + 全局订阅者（emit_scoped），影响别的插件要靠订阅
谁分配谁释放宿主绝不 free 插件的指针；宿主给的字符串是线程局部缓冲，下次宿主调用前有效

插件名与目录

  • 插件名只允许字母、数字和 . _ -（它会拼进源码和 TOML）；目录名里的 . / - 换成 _ 当 crate 名 （fuyubot.weather → fuyubot_weather）。
  • 插件名只有 dlopen 之后才知道：它来自 plugin_init 返回的 PluginHandle，所以 fuyubot plugin list 会真的加载一次再看名字。
  • 脚本插件必须让脚本与 cdylib 同名同目录（weather.dll ↔ weather.py），细节见 Python 插件 与 JS 与 TypeScript 插件。
