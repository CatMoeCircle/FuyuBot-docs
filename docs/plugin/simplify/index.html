Simplify 封装

fuyubot-simplify 的 API 参考：按功能范围分组的参数结构体、链式设置器与返回值

fuyubot-simplify 只做一件事：把 TDLib 的输入拼好、把结果等回来，返回值仍然是 TDLib 的原始 JSON （Value / Vec<Value>）。

三条贯穿全部方法的约定：

  1. 每个方法都等到结果才返回，不交回请求号；唯一的例外是 formatted（同步调用，压根没有等待）。
  2. 等待的方法是阻塞的。插件的更新回调就跑在 TDLib 接收循环那个线程上，在那里等待=自己卡自己， 等到的一定是超时。回调里一律用 *_then（见第 13 节）。
  3. 失败一律是 Err(SimplifyError)，成功时的返回值见第 14 节。

本文按功能范围分组；想知道这些方法内部怎么实现（为什么这么拼、为什么这么等）， 看开发 › simplify 封装是怎么实现的。

别的语言怎么用同一套语义

ABI v5 起这套语义不再只有 Rust 有。 宿主从 v5 开始自己跑同一份 fuyubot-simplify 代码 （fuyubot-simplify::ops），经 simplify_invoke / simplify_invoke_result 暴露成一张 op 表：

所以 Go / C / C++ / JS / TS / Python 插件都能用「发消息等结局、超时撤回、bot 与用户号挑不同反应 方法、Markdown → entities、富消息本地块树」，行为与 Rust 侧逐字一致——没有第二套实现。 完整清单与结果形状见 ABI › simplify 操作表。

Rust 插件仍然用本页这些类型化方法：它们有编译期检查与链式设置器，比拼 JSON 舒服。 ops 那层是给「没有 Rust 类型系统可用」的调用方准备的。

除了发/改/删，这一层还收了四件「TDLib 里没有直觉上那个方法」的事： 管理权 / 转发 / 表情反应 / 连接状态。

1. 文本内容：Text 与 ParseMode

带标记的文本不由本 crate 解析——经同步的 td_execute 问 TDLib 的 parseTextEntities （为什么不能用异步，见开发 › simplify 封装是怎么实现的里的「文本链路」一节）。

Prop

Type

快捷构造：Text::plain / Text::markdown / Text::markdown_v2 / Text::html / Text::new(text, mode)； &str / String 直接转成纯文本。

ParseMode发出的 parse_mode

MarkdownV2textParseModeMarkdown + version: 2

⚠️ 注意：MarkdownV2 的粗体是 *x*，不是 **x**。 **bold** 会被吞成 bold 而且不给 bold entity，__x__ 出来的是下划线。别按 CommonMark 的直觉写 ——这正是「不自己实现解析」的理由。

拿到结果也没干活不符预期：拿不到就退回纯文本并打一条 Warn 日志（没接 TDLib、TDLib 报错都一样）， 一条 Markdown 写错的消息不该整条发不出去。

话题：Topic

topic_id 不是裸 id，是 TDLib 的 MessageTopic——四个构造器各有各的 id 类型，选错了 TDLib 就拒：

构造用在哪发出的 topic_id

11. 管理权：AdminRight

TDLib 里 user 连 is_bot 都没有（身份在 user.type），管理权也不在任何「用户信息」上—— 它只在 getChatMember 给的 ChatMember.status 里。

Prop

Type

判定规则（is_admin_status）：

status.@typeright: Noneright: Some(x)
chatMemberStatusCreator（群主）truetrue——群主拥有一切（唯一例外见下）
chatMemberStatusAdministratortruestatus.rights.<x> 必须为 true，字段缺失按 false
其余四种（member / restricted / left / banned）falsefalse

⚠️ 群主的匿名是 status.is_anonymous，不在 rights 里——所以 Some(AdminRight::IsAnonymous) 对群主读的是前者。AdminRight 共 18 项，名字就是 chatAdministratorRights 的字段名 （can_manage_chat / can_delete_messages / can_pin_messages / …），认不出的字段名 AdminRight::from_key 返回 None。

拿不到成员信息（超时 / TDLib 报错 / 不是群聊）一律 false：不确定时说「没有」比说「有」安全。

12. 转发：ForwardParams

simplify.forward_messages(chat_id, from_chat_id, &params) → Result<Vec<Value>>。

Prop

Type

走的是 forwardMessages（一次一组，不是 Bot API 的 forwardMessage）。返回的是还没发完的临时消息 ——这里只等响应，不等发送结局，最终消息照旧经 updateMessageSendSucceeded / updateMessageSendFailed 回来。单项没转发成功时 TDLib 在对应位置放 null，所以数组长度与排序后的 message_ids 一致、 但元素可能是 Null。

空列表 → SimplifyError::EmptyForward，超过 100 条 → TooManyForward，两者都在发请求之前挡掉。

13. 表情反应：Reaction

bot 与用户号不是同一个方法，这一点没有「通用写法」可言：

方法用哪个 TDLib 方法语义
react(chat_id, msg, &reaction, is_big, timeout_ms)自动：bot → setMessageReactions，用户 → addMessageReaction加一个反应
unreact(chat_id, msg, &reaction, timeout_ms)自动：bot → setMessageReactions 传空列表，用户 → removeMessageReaction去掉反应
add_reaction(..)固定 addMessageReaction已知自己是用户号时省掉 getMe
set_reactions(..)固定 setMessageReactions已知自己是 bot 时；空切片 = 清空

自动判定靠 getMe 的 user.type.@type == "userTypeBot"，也就是说 react / unreact 每次会多一次 getMe 往返（它不碰服务器，TDLib 本地应答）。⚠️ bot 侧没有「删一个」的说法，只能整组覆盖—— 所以 bot 的 unreact 会忽略 reaction 参数，直接清空。

Reaction::emoji("👍") → reactionTypeEmoji；Reaction::custom_emoji(id) → reactionTypeCustomEmoji。 付费反应（reactionTypePaid）不在这套里。

14. 连接状态：ConnectionTracker

TDLib 没有 getConnectionState——连接状态只以 updateConnectionState 的形式出现， 所以「现在连上了吗」只能自己订阅并记住最新那条。

Prop

Type

两个坑：

  • 订阅之前推过的更新补不回来（TDLib 的状态更新不重放），所以在插件 start 里尽早调； 晚订阅只会漏掉开头的 Connecting / Updating。
  • 这是连接状态（到 Telegram 的链路），不是授权状态（updateAuthorizationState，登录那一套）。 两者独立：connectionStateReady 也可能还没登录。

16. 参数名为什么是这几个

真 td_api.tl：sendMessage chat_id topic_id reply_to options reply_markup input_message_content ——没有 message_thread_id / 顶层 disable_notification / 顶层 caption（那些是 Bot API 的名字）。 短名字到 TDLib 字段的映射只有一处实现：

参数结构体的字段落到的 TDLib 字段
topic_id: Some(Topic::forum(n))topic_id = {"@type":"messageTopicForum","forum_topic_id":n}
topic_id: Some(Topic::thread(n))topic_id = {"@type":"messageTopicThread","message_thread_id":n}
reply_to_message_idreply_to = {"@type":"inputMessageReplyToMessage","message_id":…}
reply_markupreply_markup = {"@type":"replyMarkupInlineKeyboard","rows":…}
link_preview: Some(false)inputMessageText.link_preview_options.is_disabled = true
text / media.captionformattedText（经 parseTextEntities）
is_chat_admin 的 user_idgetChatMember.member_id = {"@type":"messageSenderUser","user_id":…}

17. 异步版：*_then

每个等待版都有一个 *_then（send_message_then / send_message_album_then / edit_message_text_then / edit_message_caption_then / edit_message_media_then / edit_message_reply_markup_then / delete_message_then / answer_callback_query_then / forward_messages_then / react_then / unreact_then）： 把等待挪到另一个线程，立刻返回，结局交给闭包。

⚠️ 它们返回那个线程的 JoinHandle——插件要在 stop() 里 join 掉，否则动态库卸载之后线程还在跑库里的代码。

18. 返回值与错误

方法成功时返回的就是 TDLib 原始 JSON（Value / Vec<Value> / ()），没有额外包装。 带状态的返回类型只有 EntitiesResolution / EntityResult / FileDownload 三个（见第 9 节）。

Prop

Type

编辑类刻意不重试——限流该等多久是调用方的事。
