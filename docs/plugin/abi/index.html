ABI 契约

HostApiVTable、导出符号、内存所有权与版本协商

这是唯一的跨语言契约：形状只有 fuyubot-abi/src/lib.rs 一份实现，C 头文件 fuyubot_plugin.h 由 cbindgen 从它生成（产物，不是源码，别手改）。宿主侧所有桥在 fuyubot-loader/src/runtime.rs。改 ABI = 改那个文件 + 加版本号。

插件必须导出的符号

v3 的四个契约符号仍是必需/可选的底线；v4 另外导出三个静态符号，让 宿主与静态工具不 dlopen 也能看见插件是按哪个 ABI 编的（版本值仍只能运行时判定）。

符号类型必须吗说明
plugin_initunsafe extern "C" fn(*const HostApiVTable) -> PluginHandle必须校验 VTable、构造状态；返回失败句柄（abi_version == 0）= 拒绝加载
plugin_startunsafe extern "C" fn(PluginHandle, *const c_char) -> i32可选拿到配置 JSON，注册订阅 / 工具 / 中间件；返回 0 成功
plugin_stopunsafe extern "C" fn(PluginHandle)可选卸载前调一次，回收自己的状态
plugin_free_stringunsafe extern "C" fn(*mut c_char)必须释放插件自己分配的字符串（宿主从不 free 插件的指针）
plugin_free_handleunsafe extern "C" fn(PluginHandle)v4 可选版本不匹配、不能调 plugin_stop 时，用来释放 plugin_init 分配的状态
fuyubot_abi_versionunsafe extern "C" fn() -> u32v4 可选返回编译期 ABI_VERSION；静态工具只检查“存在”，值要运行时看
plugin_manifestunsafe extern "C" fn() -> *const c_charv4 可选自描述 JSON（名字 / 版本 / inject / soft_inject）。宿主在 plugin_init 之前读；名字与 init 不一致只告警，依赖以 manifest 为准

符号名由常量钉住（SYM_PLUGIN_INIT / SYM_PLUGIN_START / SYM_PLUGIN_STOP / SYM_PLUGIN_FREE_STRING / SYM_PLUGIN_FREE_HANDLE / SYM_PLUGIN_ABI_VERSION / SYM_PLUGIN_MANIFEST），PluginLoader::load_with_config 按这些名字 lib.get(...)。 C++ 里必须把它们放进 extern "C" 块，否则名字被 mangle，宿主 dlsym 不到。

PluginHandle = { abi_version: u32, size: u32, context: *mut c_void, name: *const c_char }； is_valid() 的判据是「abi_version != 0 且 context 非空」，所以插件的 context 不能是 NULL。PluginHandle::FAILED 是全零版本号，const _ 里有 assert!(PluginHandle::FAILED.abi_version == 0)。

三点值得记住：plugin_manifest 在 plugin_init 之前读（宿主得先知道你的依赖才能排顺序）； 版本不匹配时只能用 plugin_free_handle 收尾，那一刻 plugin_stop 不会被调； 卸载顺序是 plugin_stop → 回滚注册 → 最后才 drop 那个 Library。

HostApiVTable：host_ctx + 27 个函数指针

version 在偏移 0、size 在 4、host_ctx 在 8，其余 27 个是函数指针，全是 Option<...>； 总大小 = 2 * size_of::<u32>() + 28 * size_of::<*const c_void>()（host_ctx + 27 个函数）， 由 const _ 里的 offset_of! / size_of 断言钉死。每个函数第一个参数都是 host: *mut c_void。

服务作用域

每个插件加载时拿到自己的一层 Context，于是：

  • provide_service 注册的服务只对本插件（和它更深的子作用域）可见——默认私有。 两个插件注册同名服务不冲突，各用各的实现。
  • 宿主注册在根上的公共服务（事件总线 / 服务容器 / 工具表 / 中间件管线）沿父链照样看得到。
  • 真要跨插件共享才用 provide_service_shared：它写进程级的根表，同名会和别人撞 （直接报 ServiceNameExists）。
  • 插件卸载时，它那层作用域连同里面的服务一起消失。

跨插件联动的端到端示例（/help 的命令注册表）见插件联动。

两条形状上的硬要求：

  • 第一个参数总是 host: *mut c_void：裸函数指针没有捕获环境，VTable 里放不了闭包； 不给显式上下文就只能靠进程级全局，那样一个进程只能有一个宿主、测试也没法并行。
  • 每个函数指针字段都是 Option<...>：C 侧传 NULL 合法，非 Option 字段收到 NULL 就是 UB。 Rust 侧 HostApi::from_raw 一次解包校验全部 27 个，之后调用路径上没有 Option、也没有 panic 分支。

服务的形状：ServiceVTable

一个服务就是一张 C 结构表——宿主和插件都不需要知道服务的 Rust 类型，按名字调方法即可：

字段类型含义
name*const c_char服务名，NUL 结尾 UTF-8
versionu32提供方填的协议版本（协商用，宿主不校验）
sizeu32size_of::<ServiceVTable>()
context*mut c_void提供方的实例数据，原样传给每个方法
methods*const ServiceMethod指向 method_count 个连续的方法项
method_countusize方法项个数

每个方法项是 { name: *const c_char, func: ServiceMethodFn }， ServiceMethodFn = fn(context: *mut c_void, input_json: *const c_char) -> *const c_char。

怎么调方法

v6 起这次调用经过宿主（VTable 第 24 项 call_service），Rust 侧写法没变： HostApi::call_service(name, method, input_json)。

  • 宿主替你把这个调用转给提供方，并在调用期间记下调用方是谁；
  • 被调方因此能在方法里问出真实调用方（下一节），插件在自己的线程上调进来也成立；
  • 返回 NULL = 失败（服务不存在 / 没这个方法 / 入参含 NUL）；
  • 返回空串 = 成功但没有输出（对方方法返回了 NULL）；
  • 其余 = 提供方持有的 NUL 字符串，立刻拷走——它只在本次调用返回后、 下一次宿主函数调用之前有效（与 list_tools / get_config 同一套线程局部缓冲）。

失败时別只说「调用失败」：第 25 项 last_error 带着原因（哪个服务、哪个方法、为什么）。 HostApi::call_service 已经自动把它拼进错误里，Rust 侧直接 ? 就能看到：

NULL 与空串的分工是 v6 才明确的（v5 时两者都当「成功但没有输出」）。 提供方想说「成功、无返回值」请 return ""，不要 return NULL。

取值规则（v6）：正在被别人调用时就是调用方；其余时候是宿主最后把控制权交给的那个插件 （在插件自己起的线程上则是 NULL）。身份由宿主判定，插件自报不了，也拿不到别人的。 /help 的命令归属就是这么来的。

宿主预置的服务

宿主在根上预置了三个服务，任何插件沿父链都看得见，直接 call_service 就行：

服务名方法协议
fuyubot.host.pluginsreport无参 → {"plugins":[{name, state, …}]}，进程内插件快照；state ∈ active / pending / failed / activating，pending 带 missing、failed 带 reason
fuyubot.host.identityusernames无参 → ["FuyuBot"]，自身全部活跃用户名（usernames.active_usernames）；没登录 / 没接 TDLib 时是 []
me无参 → getMe 的原始 user JSON；没登录时 null
fuyubot.host.scopescope_create{} → {"handle":N}，开一个子作用域
scope_enter{"handle":N}；成功 null，失败 {"error":"…"}
scope_leave忽略入参；离开当前作用域
scope_drop{"handle":N}；成功 null，失败 {"error":"…"}

fuyubot.host.plugins 与 ABI 第 8 项 list_plugins 同源，只是多一条走服务这条路 （内置 /plugins 插件就是这么读「进程里真在跑的」插件清单的）。fuyubot.host.identity 是「我是谁」：宿主登录成功拿到 getMe 之后写进去，之后每条 updateUser（id 是自己那条） 都会刷新它，所以改名字 / 改用户名之后读到的就是新值。fuyubot-simplify 的 on_command 靠它把「点名给别人的命令」挡在插件外面——纯内存读取，不是 TDLib 请求， 在命令回调里调它不会卡接收循环。面板与 fuyubot status 显示的账户行也来自同一份数据 （经 .fuyubot/status 跨进程过去）。 fuyubot.host.scope 是中间插件批量托管脚本时开子作用域用的，见架构。

句柄类型（SubscriptionHandle / ToolHandle / ServiceHandle / MiddlewareHandle / RequestId） 都是 #[repr(C)] + 单个 u64（断言钉住 size_of == size_of::<u64>()）； LogLevel = 1..5（Error / Warn / Info / Debug / Trace），Stage = 0..5； WaitHandle = { id: u64, matched: u32, _reserved: u32, payload_json: *const c_char }。

内存所有权：三条硬规矩

  1. 谁分配谁释放。插件通过 plugin_init 返回的 name、以及插件自己分配的任何字符串， 都由插件持有；宿主绝不 free 它们。插件要给宿主一个需要接管的临时字符串，只能走 plugin_free_string 那套约定。
  2. 宿主返回的字符串是线程局部缓冲。list_tools、get_config、WaitHandle::payload_json 指向宿主的一块复用缓冲（thread_local! HOST_STRING），只在下一次调用宿主函数之前有效。 要留着就当场拷走，并且不要试图释放它——VTable 里没有 host 侧的 free 函数，这是设计不是遗漏。
  3. ServiceMethodFn 的返回值由提供方持有，调用方读完即弃。

版本 6 的改动：尾部追加 call_service（第 24 项），服务调用改成经过宿主。 宿主因此在调用期间知道调用方是谁，current_plugin 拿到的就是它——于是 「插件在自己起的线程上调服务」也认得出调用方，嵌套调用报的是直接调用者而不是最初的调用方。 同时 call_service 的返回值约定收紧：NULL = 失败，空串 = 成功但无输出。

同一次 v6 里还追加了三项（25 / 26 / 27）：last_error（失败原因）、list_services （服务发现）、set_config_section（跨插件写配置）。这三项是纯尾部追加，靠 size 协商、不再跳版本号——老宿主（没有这三项）会明确拒绝新插件，而不是读到错位的指针。

另外 set_config 的判定对象从「调用者」改成了「执行者」：服务方法里写配置现在落 提供方自己的段（以前会错写进调用方那段），get_config 不受影响。

⚠️ 这次跳了版本号（5 → 6）：字段是纯追加，但 current_plugin 的取值来源变了， 属于静默的行为差异，不能只靠 size 协商。v5 插件在 v6 宿主上、v6 插件在 v5 宿主上 都会 AbiMismatch（拒绝加载），重编一次即可（仓库里所有插件与模板都从 ABI_VERSION 取值）。 完整清单见 ABI v5 → v6 迁移。

追加字段本身不破坏老插件（它们先比 size），但按契约「改 ABI 就加版本号」， v4 / v5 / v6 各跳过一次——用旧版本编出来的插件会被宿主拒绝加载，重新编一次即可。

为什么本 ABI 一个可变参数函数指针都没有

Rust 的 extern "C" fn(.., ...) 确实稳定（能写、cbindgen 也能生成），但本 ABI 一个都没用， 理由只有一条：... 会把参数类型和个数校验全部丢掉。VTable 里 27 个函数的参数都是固定的， 用 ... 只会让 C 侧传错参数从编译错误降级成运行期 UB。

两条必须知道的事：

  • 变参部分不能是唯一的参数——C 要求 ... 之前至少有一个具名参数。
  • 变参函数指针跨不了 ABI 的 Option 优化：Option<fn(..., ...)> 不是 niche 优化，占两个指针宽， 必须显式判空。本 crate 里那条 size_of::<Option<unsafe extern "C" fn()>>() == size_of::<*const c_void>() 断言只对非变参函数指针 成立；普通函数指针字段能享受 niche 优化（NULL 就是 None），这也是「整个 VTable 所有字段都能是 Option<...> 且不撑大布局」的前提之一。

回调为什么是 C-unwind

EventCallbackFn 与 MiddlewareCallbackFn 都是 unsafe extern "C-unwind" fn(...)。 extern "C" 边界上逃出去的 panic 会直接 abort 整个进程，宿主来不及 catch_unwind； C-unwind 允许 unwind 穿过边界，宿主就能接住、记一条日志、继续跑下一条更新。 对 C/C++ 而言两者 ABI 完全一致；C++ 异常同样会穿过这个边界，请自己在回调内处理完。

define_plugin! 生成的三个导出函数还会把插件代码包在 catch_unwind 里——两层都要。

版本不兼容时宿主不会调 plugin_stop：那是对一个不认识的 ABI 下手。字段只增不改， 新增一律追加在尾部；改动必须同时抬 ABI_VERSION。

宿主 ABI 版本是 fuyubot_abi::ABI_VERSION（当前 6）；插件编译时用它做校验，不用手抄。
