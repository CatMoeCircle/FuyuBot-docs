插件联动

用共享服务互相调用、用软依赖排好启动顺序——以内置 /help 的命令注册为例

插件之间没有共享的 Rust 类型，也没有彼此的符号表。原生插件（cdylib）跑在同一个进程里， 但只通过宿主的 C ABI 打交道。想「A 把自己的能力借给 B 用」，只有宿主提供的那几条通道。

这篇讲最常用的一条：命名服务 + 软依赖。例子就是内置的 /help—— 它把命令表暴露成一个进程级服务，fuyubot.start 和 fuyubot.manage 在启动时把自己的命令登记进去， 而它们之间没有一行互相 import 的代码。

先选通道

想做的事通道有返回值对方必须在？
广播「发生了什么」，不关心谁在听事件总线 emit / 订阅否否
调一个能力，当场要结果命名服务 provide_service(_shared) + call_service是（JSON 字符串）是（调用那一刻）
让宿主 / AI 能发现并调用工具表 register_tool + call_tool是是
只要求「我启动时它已经在了」inject / soft_inject—不负责传值

服务适合「一个插件提供能力、其它插件按名字调」：命令注册表、缓存、鉴权、数据源都属于这一类。 它不替代事件——事件是通知，服务是调用。两者可以叠：服务方法内部照样能 emit。

/help 的联动结构

内置 /help 把命令表暴露成进程级服务 fuyubot.help.commands，方法有两个：

方法入参返回
register{"name":"start","description":"开始使用"}{"ok":true}；坏入参回 {"ok":false,"error":"…"}
list忽略[{"name":"start","description":"…"}, …]，即 /help 实际渲染的内容

服务名建议用反向域名（fuyubot.help.commands），方法名用动词；协议字段只增不改， 破坏性改动时把 ServiceVTable.version 加一（宿主不校验，但调用方可以据此判断）。 坏入参不要 panic——回一个带 error 的 JSON，调用方才有机会降级。

三个插件各管一段：

角色插件做什么
提供方fuyubot.helpstart() 里 provide_service_shared 注册服务；/help 渲染时合并静态基线与动态注册表
消费方fuyubot.startsoft_inject 声明软依赖；start() 里 call_service(…, "register", …)
消费方fuyubot.manage同上，登记 /plugins

消费方不链接 help 插件，也不 import 它的任何代码。它只认两个字符串——服务名和方法名—— 外加一份两边都认的 JSON 协议。

实例源码在运行时仓库的 plugins/fuyubot-plugin-help、plugins/fuyubot-plugin-start、 plugins/fuyubot-plugin-manage；这篇只摘和联动有关的部分。

提供方：把能力做成服务

下面代码用 fuyubot-abi 的类型写（三个内置插件就是这么写的）。外部 Rust 插件把 fuyubot_abi 换成 fuyubot_plugin_api 即可：后者把 ServiceVTable / ServiceMethod / Plugin / define_plugin! 原样重导出，形状完全一样。

1. 写方法

服务方法只有一个签名：收 JSON、回 JSON（或 NULL 表示「成功但没输出」）。

方法跑在调用方线程上。消费方若在命令回调（接收循环线程）里调它，这里就不能做慢事—— 否则整个宿主一起卡住。要慢慢做的活，在方法里排个队、立刻返回。

⚠️ ServiceMethodFn 是 extern "C"，方法里不能有 panic：逃出这个边界的 panic 会直接 abort 整个宿主，不是只挂你的插件。解析失败回 {"ok":false,"error":"…"}；确实可能 panic 的 代码段自己 catch_unwind。

2. 打包 VTable 与它引用的缓冲

ServiceVTable 里全是裸指针：name 指向服务名，methods 指向方法数组，每个方法项又指向 自己的名字。这些缓冲必须和 VTable 活一样久，所以打包进同一个结构体，一起放进 Box：

这里有几个容易写错的点：

  • Vec 的堆缓冲在结构体移动时不会跟着搬，所以 Box::new 之后 names[i].as_ptr() / methods.as_ptr() 仍然有效。别在注册之后再 push——重新分配会让宿主手里的指针悬空。
  • version 是提供方自己的协议版本，宿主不校验；它只用于调用方自己判断。
  • context 会原样传给每个方法。需要实例状态就把 self 指针放这里；/help 用的是进程级 static 注册表，所以留空。

3. start() 注册，stop() 放下

跨插件共享必须用 provide_service_shared。 provide_service 写的是调用者自己的 子作用域，兄弟插件沿父链往上看不到它；两个插件各注册一份同名私有服务也不会冲突， 但也就谈不上联动。_shared 写进程级的根表，同名会和别人撞——所以它必须显眼。

ServiceHandle 不是 RAII：它没有 Drop，丢在一边不会注销。正常也不需要手动注销—— 插件卸载时宿主按 owner 回滚它注册的一切，共享服务也一样（写在根表也记得 owner）。 这里的 Option<Box<HelpService>> 只是为了保活 VTable，不是为了「用句柄控制注册」。

4. 提供方也要能单独活

/help 的静态基线 BUILTIN_COMMANDS 始终包含 start / help / plugins 三个命令； 动态注册表只是叠加，渲染时按名字去重。所以：

  • 没有消费方登记命令，/help 仍然列得出内置三件套；
  • 消费方没起来，只是少几条动态说明，不会让 /help 整个失效。

这是可选联动的通用做法：提供方给自己留一份能独立工作的兜底，别把「有人来调我」 当成自己启动的前提。

消费方：按名字调用 + 软依赖

fuyubot.start 的接线只有两段：start() 里调服务，soft_inject() 里声明排队偏好。

call_service 是普通安全函数，返回 Result<String, AbiError>：

  • 服务不存在 / 方法不存在 / 方法指针是 None → Err；
  • 方法返回 NULL → Ok(String::new())（「成功但没输出」）；
  • 方法返回字符串 → 立刻拷成 String，调用方拿到的是自己的一份，可以随便留着。

⚠️ 目前错误类型不细分「服务不存在」和「没有这个方法」，都是 AbiError::BadString。 所以日志里要把服务名、方法名一起打出来，否则排查时只看得到一句「失败了」。

soft_inject 做了什么、没做什么

宿主在 plugin_init 之前读 plugin_manifest 里的依赖列表（define_plugin! 会把 Plugin::soft_inject() 写进去）。同步阶段分两轮：

  1. 先激活「硬依赖齐 且 软依赖也齐」的插件；
  2. 再激活「只有硬依赖齐」的插件。

所以同一批加载时，只要 help 能正常起来，它一定先于 /start 和 /plugins 激活—— 不管文件名的字典序怎样。

但它不是「提供方一定在」的保证：

  • 如果 help 自己卡在硬依赖上（停在 Pending），消费方的软依赖就不算齐，第二轮照样会激活 消费方。这时 call_service 会失败。
  • 如果 help 的 start() 报错（Failed），软依赖同样不阻塞消费方。
  • 运行期中提供方被卸载，消费方仍然处于 Active、不会重新跑 start()；之后的每次调用 都要自己处理错误。

一句话：软依赖管排队，不管可用性。所以上面的 match 分支不是客套，是必须的。

软依赖写服务名还是插件名？

inject / soft_inject 里的名字，宿主认两种：

写法宿主查什么什么时候用
服务名（"fuyubot.help.commands"）根作用域的 Context 里有没有这个名字推荐。换一个插件提供同名服务，排序仍然成立
插件名（"fuyubot.help"）有没有同名插件处于 Active只关心「那个插件」而不是「那个能力」时

⚠️ 软依赖写私有服务名是排不上序的：兄弟插件看不到它，管理器在根作用域里也查不到。 跨插件的能力一律走 provide_service_shared，依赖也写同一个服务名。

软还是硬？

场景选择
没有 /help 也要能跑，只是少一条登记soft_inject + 运行期降级
没有数据库 / 鉴权就完全没意义，宁可别启动inject（硬依赖）
只要求「它先起来」，不直接调它的服务soft_inject 写插件名
能力名稳定、可能有替代提供者soft_inject 写服务名

硬依赖的语义是准入：缺了就不激活，停在 Pending 等；如果提供它的插件已经 Failed， 依赖方会被级联标成 Failed，而不是永远假装在等。但它也不传值——到了 start() 里， 你仍然要自己 get_service / call_service。

依赖声明不要写进配置：manifest 是权威来源，define_plugin! 从 trait 自动生成。 只有没有 plugin_manifest 的 v3 老插件，宿主才回退到 [plugin.<名字>].inject / .soft_inject（manifest 该侧非空时覆盖配置，不是合并）。见插件总览。

排查

  • /help 里少了一条命令：先看 start / manage 的日志有没有 … 已向 /help 注册命令：{"ok":true}；失败那条会带 call_service 的错误。
  • 服务注册失败：宿主日志里有一行 注册共享服务 … 失败: 命名服务 … 已经注册过了 （或「收到了空 vtable」）。
  • 谁在跑、谁在等：/plugins 走宿主预置的 fuyubot.host.plugins 服务，会列出 active / pending（带 missing）/ failed（带 reason）；fuyubot status 读的是 实例发布的同一份快照（摘要 + pending / failed 明细）。
  • 依赖声明从哪来：plugin_manifest。激活时日志里那行 激活 <名字> v<版本>（硬依赖 N、软依赖 M） 就是宿主实际读到的数量；status 里的 pending / missing 也是按它算的。别只改配置——manifest 非空时配置那份会被覆盖。

一页检查清单

  • 提供方用 provide_service_shared，方法名和 JSON 协议写进文档。
  • VTable、方法数组、名字缓冲装在同一个 Box 里，注册后不再扩容。
  • 检查 ServiceHandle::is_valid()；stop() 里放下持有物，不手动 free 宿主的东西。
  • 消费方对 call_service 的失败有降级分支，不 unwrap。
  • 可选联动用 soft_inject，并接受「提供方可能不在」；缺了就活不了才用 inject。
  • 方法里不做慢活、不阻塞调用方线程；也不让 panic 逃出 extern "C" 边界。
