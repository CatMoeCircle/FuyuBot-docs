运行与实例管理

前台/后台运行、status、stop 与单实例锁

一个目录一个实例

实例状态放在 <项目根>/.fuyubot/ 下的三个文件里，三件事各占一个文件：

文件作用
.fuyubot/lock只用来独占（try_lock，进程死即释放）。里面不存内容——Windows 的文件锁是强制的，别的进程读不到被锁的字节
.fuyubot/statuskey=value：pid / started / version / plugins / name。启动完成之后才发布（拿上锁只说明进程活着）
.fuyubot/stop停止请求，内容是 PID。fuyubot stop 先写它，让实例自己收摊
  • 第二次 run（前台后台都算）会被拒，报错里带上在跑的那个 PID。
  • 陈旧的 lock 不用手工清理：拿锁时会顺手删掉上一个实例的 status / stop。
  • --replay 不占锁、不发布状态：离线开发路径不该和跑着的实例互斥。

前台运行

顺序是固定的：自动 init → 拿单实例锁 → attach TDLib → 问/读凭据 → 加载全部插件 → 发 setTdlibParameters 并登录 → getMe 打印账户 → 发布状态 → 最后才开分发。插件先于登录加载，是为了不漏掉登录窗口里的更新。

参数作用
--config <路径>配置文件，默认 fuyubot.toml
--plugin-dir <目录>覆盖配置里的插件目录
--api-id <ID>覆盖配置里的 api_id（不是秘密）。优先级：--api-id → TG_API_ID → 配置 → 交互提问；api_hash 没有对应参数
--no-login只起框架、不走登录流程（CI / 容器；已有 session 仍会被 TDLib 打开）
--no-tdlib不接 TDLib，只加载插件
--background放到后台跑
--replay <JSON> / --replay-wait <MS>见 离线回放

凭据来源（按序）：TG_API_ID / TG_API_HASH → 配置里已保存的 [telegram].api_id / .api_hash → 交互式提问。交互问出来的会被写回配置文件，下次冷启动不用再输（这两个值每次都要随 setTdlibParameters 发出去，session 有效也一样）。Bot Token 仍只认 TG_BOT_TOKEN 或交互输入、不落盘，详见 环境变量。

后台运行

它派生一个没有终端的自己，stdout/stderr 追加进 <目录>logs\fuyubot.log；父进程等子进程真起来（.fuyubot/status 发布）才返回。

后台跑没有 stdin。要交互式登录的场合（还没有 session、也没给 TG_BOT_TOKEN）会直接失败，并把日志尾巴打出来指路——先用前台 run 或 fuyubot login 登一次，session 会落在 data/。首次连 api_id / api_hash 也问不了：先在前台跑一次让它写回配置，或设好 TG_API_ID / TG_API_HASH。

想单独把登录走完而不起框架，用 fuyubot login；要退出登录（清掉本地会话）用 fuyubot logout。

看状态

status 只读 .fuyubot/，不加载插件、不接 TDLib。三种结果：运行中 / 陈旧（没人在跑，附上次的 pid 与启动时间）/ 没有运行中的实例。还有一种是「有实例在跑、但状态还没发布」，也就是卡在启动里。

停掉

stop 的机制：写 .fuyubot/stop → 实例每 500 ms 看一次 → 停接收循环 → 卸载插件（跑 plugin_stop）→ 停内核 → 放锁；8 秒不理会才硬杀兜底。硬杀跑不到插件的 plugin_stop，所以别一上来就 taskkill。

Ctrl-C 仍是硬杀：捕获它要开 tokio 的 signal feature（会带进 mio + signal-hook-registry + errno，依赖白名单没放行）。要优雅退出就用 fuyubot stop，别按 Ctrl-C。

常见情形

现象处理
重复 run 报「已经有实例在跑」，带 PID先 status，再 stop；不要手工删 lock
status 说陈旧正常，陈旧状态不用清理，下次 run 自己接管
后台启动后立刻 status 报「启动中」状态是在插件加载 + 登录之后才发布的，等一会儿再看
进程活着但没更新没登录就收不到任何更新；先用 --replay 验插件
