配置文件

fuyubot.toml 的字段与默认值

fuyubot run 读 fuyubot.toml，所有键都有默认值。缺这个文件时 run 会按模板自动生成一份（等价于先跑一次 fuyubot init）——--replay 是例外，它不会为了回放在你的目录里留配置。

键默认值它决定什么

[telegram].account_typebot登录走哪条路：bot → Bot Token；user → 手机号 / 扫码。写错报错，不会静默当 bot

插件自己的配置段

每个插件在 [plugin.<插件名>] 下可以有自己的配置，键值任意、可嵌套。插件名是点分的 （define_plugin! / 脚手架里登记的那个名字，如 fuyubot.manage），所以在 TOML 里自然写成 嵌套表——[plugin.fuyubot.manage] 就代表插件 fuyubot.manage 那段：

插件在运行时读它、写它，走的是 ABI 接口（不是 plugin_start 的那个 config_json）：

  • 读：get_config(section, key) —— 读任意段（自己的 + 别人的）。section 空串读顶层 （[bot] / [telegram] 等），key 空串读整段，key 是点路径（nested.k）。
  • 写：set_config(key, value_json) —— 只能写自己名下的段（没有 section 参数，宿主按调用者身份判定，插件无法伪造）。成功会写内存并回写 fuyubot.toml。

各语言的写法：Rust 插件、C / C++ 插件、 Python 插件、JS / TS 插件（每页都有「读 / 写配置」一节）， 函数签名在插件 ABI。脚本插件读自己那段还有个同步入口 （plugin_config() / pluginConfig()），run() 之前就能用。

set_config 回写是「全量重写」：fuyubot.toml 里你手写的注释、空白会被 toml 序列化丢掉。插件写配置属于程序化修改，这是简单且可预期的一步；要保注释就把插件要写的值也手工维护进文件、别让插件运行时去改。唯一会被保住的是 [telegram].api_hash——它不在插件能读到的配置树里，回写时会从磁盘补回来。

凭据的边界：api_id 与 api_hash 是例外——它们每次冷启动都要随 setTdlibParameters 发给 TDLib（session 还有效也一样），不记住就得每次手输，所以 fuyubot run 交互式问过之后会把它们明文写回 [telegram] 段。这意味着这份文件从此带着你的应用密钥：别提交进版本库、别整份发给别人。不想落盘就设 TG_API_ID / TG_API_HASH（环境变量优先，且不会被写回）。Bot Token、手机号、验证码、两步验证密码仍然一律不落盘，只认环境变量或交互输入（连日志也不许出现）。session 由 TDLib 自己落在 data_dir，配置里不记任何登录态。

几条约定

  • 相对路径相对配置文件所在目录（也就是项目根）：plugins、data、日志目录都按它解析。
  • 自动 init 只认默认文件名：缺 fuyubot.toml 时 run 会生成一份；但用 --config 别的名字 时不会凭空造，直接报错。
  • status / stop 不替你造配置：找不到 fuyubot.toml 就报「先 fuyubot init 建一个」——面对的是已经存在的实例，凭空建一个只会更迷惑。
  • --plugin-dir 覆盖 [plugins].dir，--config 换配置文件本身。
  • 想知道某一行到底生效成了什么（含默认值）：fuyubot config 直接打出来，见 fuyubot 命令参考。
  • 字段读出来后，运行参数（凭据来源、加载顺序）见 运行与实例管理；account_type 之外没有别的自定义登录入口。

改了配置怎么生效

配置在 run 启动时读一次。改完要重启实例：

--replay 不占单实例锁，所以它可以和跑着的实例并存、跑完就退，适合改插件期间反复试。

改完先别急着重启：fuyubot config --config demo\fuyubot.toml 会打印生效值，account_type 之类写错时当场就能看出来（那一行是 ⚠️ 开头，而 run 要走到登录才报）。
